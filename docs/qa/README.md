# 기능별 AI QA와 사용자 승인

개발·자동 검증·기능 커밋 → AI의 실제 브라우저 QA → 실패 수정·커밋·재검증 → 사용자 결과 확인·승인 → 다음 기능 순서로 진행한다. 자동 테스트와 AI QA 통과는 사용자 승인을 대신하지 않는다. 이 절차는 2026-10-03 사용자가 확정했다.

## 역할 분담

| 담당 | 책임 |
| --- | --- |
| 주 에이전트 | 개발·자동 테스트·커밋, 브라우저 QA 실행, 실제 결과·증거 기록, 결함 수정·재검증, 사용자에게 결과 요약 |
| QA 서브에이전트 | 수용 기준 대비 누락된 경계·기대 결과·검증 증거 검토. 코드만 읽고 브라우저 케이스를 통과 처리하지 않음 |
| 사용자 | 필요한 Kakao 로그인·계정 전환, 핵심 흐름의 사용감 확인, 남은 문제·미실행 범위 검토와 최종 승인 |

- 기본 구성은 주 에이전트가 브라우저를 실행하고 QA 서브에이전트가 검토한다. 실행을 위임할 때도 한 번에 한 에이전트만 브라우저를 조작하며 담당 범위와 현재 상태를 전달한다.
- QA 서브에이전트에도 같은 접근 제약이 적용된다. 사용할 수 없으면 주 에이전트가 검토하고 독립 검토 미실행을 기록한다.
- 사용자가 전체 목록을 다시 실행할 필요는 없다. AI가 실행한 결과를 요약하고, 사용자에게는 짧은 핵심 흐름과 판단이 필요한 잔여 항목만 안내한다.
- 접근 가능한 브라우저와 로그인 상태를 먼저 확인한다. 로그인은 사용자가 직접 수행하며 비밀번호·인증번호·세션 쿠키 전달을 요구하지 않는다. 두 계정 검증은 분리된 로그인 환경 각각에 접근 가능한지 확인한다.
- 장애 재현·화면 크기 조절 등은 현재 도구가 지원하는 범위에서 실행한다. 막힌 케이스는 이유·필요한 도움을 기록하고 독립적으로 가능한 QA는 계속한다. 사용자에게 전체 목록을 되돌려 맡기지 않는다.

현재 진행 상태와 다음 작업은 [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md)에만 요약한다. 이 폴더는 상세 검증 근거를 보존한다. 이전 기능 전체를 소급해 다시 검증하는 절차는 아니며, 현재 미확인 사항부터 적용한다.

## 진행 절차

1. **AI 구현·준비**: 수용 기준을 코드와 대조하고 자동 검증을 실행한다. 기능 문서에 준비 조건, 순서, 기대 결과, 실패·권한·중복 경계와 미실행 범위를 작성한다. 제품 코드와 시나리오를 기능 단위로 커밋한다.
2. **검증 인계**: 커밋 후 실제 코드 커밋과 문서 링크를 전달한다. 문서 안에서 자기 자신의 커밋 해시를 미리 만들 수 없으므로 최초에는 `이 문서를 포함한 기능 커밋`으로 적어도 된다. 검증 시작 시 `git rev-parse --short HEAD`와 `git status --short`로 실행한 리비전·미커밋 변경을 기록한다. 기존 문서를 추가하는 이번 작업은 이미 확정된 코드 커밋을 적는다.
3. **AI QA 실행·검토**: 주 에이전트가 기본·지원 시나리오를 실행하고 각 케이스를 `통과 / 실패 / 미실행 / 보류`로 표시한다. 실행자·날짜·실제 관찰·필요한 스크린샷 또는 로그 근거를 남긴다. QA 서브에이전트가 누락·판정 근거를 검토한다. 예상 결과를 읽은 것만으로 통과 처리하지 않는다.
4. **실패 수정**: AI는 재현·수정과 필요한 자동 테스트를 수행하고 별도 수정 커밋을 만든다. 같은 검증 문서에 수정 커밋, 재검증 대상 ID와 결과를 남긴다. 이전 실패 기록을 지우지 않는다. 동작이 바뀌면 제품 문서와 기대 결과도 함께 갱신한다.
5. **사용자 결과 확인·승인**: AI가 검증한 코드·통과 범위·수정 내용·남은 문제·미실행 이유와 짧은 사용감 확인 흐름을 요약한다. 사용자는 핵심 흐름과 결과를 확인하고 실패·보류·미실행의 처리 방침이 정리된 뒤 명시적으로 승인한다. 예: `AI QA 결과와 사용감 확인, 남은 항목 X는 보류하고 다음 단계 진행 OK`. 일부만 확인했다면 해당 범위만 승인한다. AI가 승인자를 대신하거나 미응답을 승인으로 간주하지 않는다.
6. **기록·다음 기능**: 승인 범위·날짜·대상 코드 커밋·남긴 예외를 기능 문서와 현재 컨텍스트에 반영한다. 이후 확정된 다음 기능을 시작한다. 기능 문서와 결과 갱신은 기능/수정 커밋 또는 별도 `docs:` 커밋으로 보존하고 push는 별도 지시를 따른다.

상태는 `AI QA 대기 → AI QA 중 → 수정·재검증 필요 → 사용자 승인 대기 → 승인`을 사용한다. 결함이 없으면 AI QA 중에서 사용자 승인 대기로 이동한다. 새 코드 변경이 기존 승인의 범위에 영향을 주면 관련 케이스는 다시 AI QA 대기로 전환한다.

## 새 세션에서 재개

1. `AGENTS.md`, `docs/README.md`, `docs/PROJECT_CONTEXT.md`와 Git 상태를 읽는다.
2. 현재 QA 문서의 대상 코드·실행 결과·결함·사용자 승인 여부를 확인한다. 승인 전이면 현재 기능 QA·수정부터 이어간다.
3. 브라우저 연결·로그인·로컬 테스트 데이터는 세션마다 확인한다. 과거 브라우저 핸들이나 서브에이전트가 유지된다고 가정하지 않는다. 필요한 QA 담당은 새로 구성한다.
4. 기존 증거와 동일 코드에서 완료한 검증을 무조건 반복하지 않는다. 변경 영향과 남은 케이스를 기준으로 재개하고, 담당자·다음 행동을 현재 컨텍스트에 갱신한다.

프로세스에 대한 동의와 특정 기능의 최종 승인은 구분한다. 이 절차를 확정했다는 이유로 미검증 기능을 승인 처리하지 않는다.

## 작성·결과 기록 기준

- 한 기능에 Markdown 한 파일을 사용한다. 공통 절차는 이 문서만 고치고, 케이스는 PRD·플로우·화면 명세를 참조한다.
- 각 케이스에는 고유 ID, 준비/실행 순서, 눈으로 판정 가능한 기대 결과, 실제 결과를 둔다.
- 정상 흐름 외에 입력 경계, 재시도·중복, 권한, 실패 복구, 새로고침·재진입, 모바일과 영향받는 기존 기능을 포함한다.
- **기본 검증**은 AI가 일반 UI로 실행한다. **지원 검증**은 AI가 DevTools·로컬 테스트 데이터 등 준비 후 실행하며 사용자 도움은 필요한 부분만 요청한다. **자동 검증**은 DB 불변식 등을 확인한다. 각 범위의 미검증을 다른 범위의 통과로 덮지 않는다.
- 장애를 재현하지 못하면 `미실행(사유)`로 기록한다. 응답 유실, SDK 초기화 실패, 타일 다운로드 실패를 서로 같은 테스트로 취급하지 않는다.
- 실제 계정의 비밀번호·세션 쿠키·초대 토큰은 기록하지 않는다. 계정은 A/B로, 화면과 주소는 필요한 부분만 남긴다.
- 새 도구나 테스트 관리 서비스를 도입하지 않는다. 반복 비용이 확인되면 해당 흐름의 브라우저 자동화를 검토한다.

새 기능 문서에 사용할 최소 구조:

```markdown
# 기능 이름 검증
- 상태: AI QA 대기
- 대상 코드: 이 문서를 포함한 기능 커밋
- 기준 문서: PRD AC-xx / 사용자 플로우 / 화면 S-xx
- 실행 환경·날짜·검증자·실행 HEAD·미커밋 변경: 미기록
- QA 검토자·검토 결과: 미기록
## 준비
## 기본 검증
| ID | 준비·순서 | 기대 결과 | 실제 결과·실행자·증거 |
| --- | --- | --- | --- |
## 지원 검증·자동 검증과 한계
## 결함·재검증
| ID | 실제 현상·재현 조건 | 수정 커밋 | 재검증 결과 |
| --- | --- | --- | --- |
## 승인
- 사용자 승인: 대기
- 승인 날짜·대상 코드·범위: 미기록
- 보류/미실행 항목과 사용자 처리 결정: 미기록
## 사용자에게 전달할 요약
- 검증 코드·통과 범위·수정 사항:
- 남은 문제·미실행 이유·필요한 도움:
- 짧은 사용감 확인 흐름:
```

실행 결과는 AI가 기록한다. 사용자가 추가로 확인한 결과는 문서를 직접 편집하거나 아래 형태로 채팅에 알려주면 된다. AI가 받은 사실만 문서에 반영한다.

```text
실행 HEAD / 브라우저 / 화면 폭:
통과: MP-01, MP-02
실패: MP-03 — 순서, 기대와 달랐던 결과, 가능하면 스크린샷
미실행 또는 보류: MP-S02 — 이유
다음 단계 승인: 아직 / 검증한 범위와 예외를 명시한 OK
```

## 기존 자동 테스트

Node.js `24.18.1`에서 `pnpm test`로 실행한다. 2026-10-03 재실행 결과: **17개 통과, PostgreSQL 테스트 1개 기본 skip**(하위 테스트 포함 집계). 테스트 코드가 있다고 모든 기능의 단위 테스트나 브라우저 E2E가 있다는 뜻은 아니다.

| 코드 | 확인하는 범위 | 한계 |
| --- | --- | --- |
| [space-name.test.mjs](../../server/modules/space/space-name.test.mjs) | 이름 공백·빈 값·길이·이모지 | 공간 생성 요청 전체는 아님 |
| [invitation-crypto.test.mjs](../../server/modules/invitation/invitation-crypto.test.mjs) | 토큰 재생성·해시·서명·만료·키 길이 | Kakao 로그인·초대 브라우저 흐름은 아님 |
| [place-candidate.test.mjs](../../server/modules/place/place-candidate.test.mjs) | Kakao/직접 등록 필드 정규화·ID·좌표·URL·필수값 | 실제 외부 검색과 UI는 아님 |
| [search-location.test.mjs](../../src/features/place/lib/search-location.test.mjs) | 주소 우선·근처 장소 대체·0건·오류 | Kakao를 모킹하며 실서비스 응답은 확인하지 않음 |
| [manual-place.test.mjs](../../prisma/tests/manual-place.test.mjs) | 실제 `saveManualPlace`와 PostgreSQL의 동시성·권한·격리·원자성 | `pnpm db:test-manual-place`로 별도 실행. 세션/Server Action/브라우저는 포함하지 않음 |
| [prisma/tests](../../prisma/tests)의 SQL smoke 5개 | 제약·공간 생성·초대·Kakao 추가·추천의 SQL 데이터 처리 | 제품 TypeScript 유스케이스를 직접 호출하지 않음 |

DB smoke 명령은 `package.json`의 `db:test-*`를 따른다. 실제 로그인, 지도, 반응형 화면, 사용자에게 보이는 알림과 두 계정의 연결된 흐름은 브라우저 QA로 보완한다. 위 `pnpm test` 결과는 최초 QA 문서 작성 시 재실행한 기록이며 기존 DB/build 결과는 기능 커밋 시점의 기록이다.
